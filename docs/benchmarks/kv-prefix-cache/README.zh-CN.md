# llama.cpp KV 前缀缓存中间件：重启后耗时降低约 85%

[English](README.en.md)

本页展示 llama.cpp KV 前缀缓存中间件在 Hermes Agent 场景中的一次完整实测。重点不是展示缓存文件本身，而是验证一个实际效果：模型重启、Agent 新建对话后，中间件能否恢复磁盘中的 KV 前缀，让模型减少重复的前缀处理。

原始环境记录见：[测试环境.md](测试环境.md)。

## 核心效果

> **模型重启后复用已保存 KV，平均模型处理时间从 91.0 秒降至 13.7 秒：减少 77.3 秒，耗时降低约 85.0%。**

这是本次测试环境下三次独立复测的平均结果。每次复测都重新启动 llama.cpp 和 Hermes Agent，模型进程内没有保留上一轮运行状态；KV 快照由中间件保存并在下一次请求前恢复。

| 对比 | 透明路由冷启动 | 中间件恢复 KV 后 | 中间件带来的变化 |
| --- | ---: | ---: | ---: |
| 平均模型处理时间 | **91.0 秒** | **13.7 秒** | **减少 77.3 秒（耗时降低约 85.0%）** |
| 三次实测 | 1:46、1:24、1:23 | 0:12、0:13、0:16 | 每次复用均明显低于基线 |

换一种更直观的看法：恢复 KV 后的平均耗时约为透明路由基线的 **15.1%**，本组端到端模型处理时间约缩短至原来的 **1/6.6**。

这意味着：稳定的系统提示词、工具列表等前缀只需建立一次；模型重启或新建对话后，中间件仍可将已保存的前缀恢复给 llama.cpp，后续请求可以更快进入用户问题处理阶段。对需要频繁重启模型、切换窗口或重复使用相同 Agent 配置的场景，这正是中间件的主要价值。

## 结论摘要

测试过程中，每次运行都会重新启动 llama.cpp 和 Hermes Agent，尽量排除进程内已有缓存的影响。结果如下：

| 场景 | 次数 | 模型处理时间 | 平均值 | 说明 |
| --- | ---: | --- | ---: | --- |
| 透明路由，未启用中间件功能，冷启动 | 3 | 1:46、1:24、1:23 | **1:31.0** | 基线组 |
| 启用中间件，首次建立 KV | 3 | 1:30、1:29、1:28 | **1:29.0** | 建立快照阶段，包含前缀处理和保存成本 |
| 重启模型后复用已保存 KV | 3 | 0:12、0:13、0:16 | **0:13.7** | 相比基线平均减少约 **77.3 秒（85.0%）** |
| 使用同一 KV 回答不同问题 | 2 | 0:29、0:24 | **0:26.5** | 当前素材中的可核验样本；问题和输出长度不同 |
| 不使用中间件回答另一问题 | 1 | 1:27 | 1:27.0 | 只有一个样本，不作为严格统计对照 |

这组实测呈现出清晰的阶段差异：首次建立 KV 的耗时与透明路由冷启动接近，因为这一阶段需要完成完整前缀处理和快照保存；真正的收益出现在后续恢复和复用阶段。模型重启后，三次复用测试平均只需 13.7 秒，相比 91.0 秒的透明路由基线减少 77.3 秒，耗时降低约 85.0%。

表格和图片统一记录 Hermes 测试界面显示的模型处理时间；平均值按对应测试组中实际可核验的样本计算。

## 测试流程

### 1. 透明路由基线

1. 启动中间件，但输入 `stop`，只保留透明路由；
2. 干净重启 llama.cpp，避免使用它自己的进程内 KV；
3. 启动 Hermes Agent；
4. 发送相同的初始问题，等待 Agent 完成回答；
5. 关闭并重启 Hermes Agent，重复三次；
6. 记录测试界面显示的模型处理时间。

### 2. 首次建立 KV

1. 启用中间件缓存功能；
2. 干净重启 llama.cpp 和 Hermes Agent；
3. 发送相同的初始问题；
4. 等待中间件提取稳定前缀、完成预填充并保存 KV；
5. 重复三次并记录时间；同时使用 `list` 命令确认 KV 状态为 `ready`。

这组结果衡量的是“建立缓存的首次成本”，不是缓存复用收益。建立成功的终端记录也作为结果证据保留在下方。

### 3. 重启后复用 KV

1. 保留中间件保存的 KV 快照；
2. 重启 llama.cpp，清空模型进程内的 slot 状态；
3. 重启 Hermes Agent，创建新的对话窗口；
4. 发送相同前缀下的请求；
5. 记录中间件从磁盘恢复 KV 后的响应时间；
6. 重复三次。

### 4. 不同问题验证

使用已经保存的稳定前缀，但更换用户问题，观察缓存是否仍能被复用。当前素材目录中提供了两张该组结果图，因此这里展示两条可核验样本。由于问题复杂度、回答长度和工具调用路径不同，这组结果只用于验证“缓存前缀不绑定单个用户问题”，不适合与前三组做严格的一对一速度比较。

## 效果解读

- “首次建立 KV”与“复用 KV”是两个不同阶段，不能把首次建立缓存的耗时当作复用耗时。
- 首次建立 KV 的三次模型处理时间为 1 分 30 秒、1 分 29 秒、1 分 28 秒，平均 **1 分 29.0 秒**；这包含完整前缀处理和快照保存成本。
- 重启后复用 KV 的三次模型处理时间为 12 秒、13 秒、16 秒，平均 **13.7 秒**；透明路由冷启动三次平均为 **91.0 秒**，复用阶段平均减少 **77.3 秒（约 85.0%）**。
- 三次复用结果都明显低于对应的冷启动基线，说明收益来自中间件恢复的稳定前缀，而不是某一次偶然的单次计时。
- 当前两条不同问题样本的模型处理时间为 29 秒和 24 秒，平均 **26.5 秒**。由于问题内容、输出长度、工具调用和 Agent 展示逻辑不同，这组数据不应被当作严格的速度对照。
- 最终是否命中 KV，应同时检查中间件日志中的 `prefix_cache_restored` / `prefix_cache_result` 和模型响应中的 `cached_tokens`。截图中的计时只能证明端到端耗时变化。

## 限制与下一步

本页面没有记录每次请求的精确 Prompt Token、`cached_tokens`、TTFT、模型生成 Token 数和磁盘恢复耗时，因此它是一份“用户可感知的端到端效果展示”，不是严格的微基准测试。

后续更严谨的测试应固定：用户问题、最大输出 Token、工具调用路径、模型采样参数和后台负载，并分别记录：

1. llama.cpp 前缀预填充耗时；
2. KV 快照磁盘恢复耗时；
3. 新增 Prompt Token 数；
4. `cached_tokens`；
5. 首 Token 延迟和完整响应耗时。

复现时请将命令中的模型路径、端口和快照目录替换为本机值。页面展示的命令文本已经使用占位路径，不包含本机启动参数截图。
